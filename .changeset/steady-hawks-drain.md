Ingest and digest run on less memory and CPU, and get through a burst faster. The spawned digest task is boxed only once it holds a processing slot, so a backlog of queued events no longer carries a multi-kilobyte state machine per event: peak RSS during a 20k-event burst drops from ~195 MB to ~55 MB. The recovery worker skips events that a task in this process already owns, which under load had it replaying the whole queue on top of the running digests (thousands of failed reads and duplicate digests per scan). The pending-file store runs as one blocking-pool round trip instead of nine `tokio::fs` hops, and every digest issues fewer statements: the project and installation rows are read once, the grouping and its issue come back in one JOIN, the event insert no longer round-trips the payload through `RETURNING *`, the platform inference UPDATE is skipped once a project has a platform, and the rate-limit window counts use the `(project_id, digested_at)` index instead of a full scan. On SQLite, digests take turns at the write lock in process rather than through the busy handler's polling sleeps, and the durability checkpoints that gate file deletion are batched on a background queue instead of running per digest, off the path that holds the processing slot. Measured on a 4-core box against SQLite (20k events, 32 connections): ingest ~2.3k → ~4.9k req/s with p99 27 ms → 12 ms, digest ~510 → ~1000 events/s, server CPU per 20k events 56 s → 31 s.
