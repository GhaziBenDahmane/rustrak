# Try 0.15 (release candidate)

Rustrak 0.15 is the release where **the server serves the dashboard**. It is
available as a release candidate for anyone who wants to run it ahead of the
release. Everything else on this site describes 0.14, the stable line, until
0.15 ships.

## What changes

- **One container.** The dashboard is compiled to static files that the
  server hands out at `/`, so the same process answers the page and the API.
  Open the server's own address, `:8080` by default, and sign in there. The
  `rustrak-ui` container, `RUSTRAK_API_URL` on the server side, and the
  second port are no longer needed.
- **One origin.** The browser calls the API on the origin it loaded the page
  from, so the session cookie is first-party and no CORS applies to the
  dashboard. Behind a reverse proxy there is one upstream to configure.
- **The sign-in page is at `/login`**, where it was `/auth/login`. `/auth` is
  the API's namespace, and now that the page and the API share an origin it
  cannot also be a page. Every other address is unchanged.
- **The dashboard is still optional.** `RUSTRAK_DASHBOARD=off` keeps the
  server API-only, and an image built without a dashboard serves the API and
  nothing else, as it always has.
- **`rustrak/rustrak-ui` still exists**, now as nginx serving the same bundle
  and proxying the API to `RUSTRAK_API_URL`, for the installation that keeps
  the dashboard on a different host from its data. It is about 30MB and idles
  under 15MB. On the same host as the server it buys nothing.
- **The dashboard is a Vite and TanStack Router application** instead of
  Next.js. Nothing about it looks or behaves differently; the framework is
  what made the rest possible.

The database schema is the one 0.14.13 introduced. Moving to 0.15 and back
touches no data.

## Run it fresh

```bash
docker run -d \
  --name rustrak \
  -p 8080:8080 \
  -v rustrak_data:/data \
  -e SESSION_SECRET_KEY=$(openssl rand -hex 32) \
  -e CREATE_SUPERUSER=admin@example.com:changeme123 \
  rustrak/rustrak-server:next
```

Open **http://localhost:8080** and sign in. `next` follows the latest release
candidate; `rustrak/rustrak-server:v0.15.0-rc.0` and its `-postgres` twin
pin one. `latest` and `postgres` keep pointing at 0.14 until 0.15 ships.

The npm packages follow the same rule: `npm install @rustrak/client@next`
and `@rustrak/mcp@next`.

## Move an existing 0.14 installation

Three edits to your `docker-compose.yml`, and the data stays where it is:

1. **Change the server image** to `rustrak/rustrak-server:next` (or
   `:next-postgres` if you were on `:postgres`).
2. **Delete the `ui` service.** Its `RUSTRAK_API_URL` goes with it; nothing
   replaces it.
3. **Publish the server's port**, if the dashboard was the only thing you
   exposed: the `ports` block of `server` is now the address people open.

```diff
 services:
   server:
-    image: rustrak/rustrak-server:latest
+    image: rustrak/rustrak-server:next
     ports:
       - "8080:8080"
     environment:
       - SESSION_SECRET_KEY=${SESSION_SECRET_KEY}
       - PUBLIC_URL=https://rustrak.example.com
+      # Issue links in notifications now point at the server itself.
+      - DASHBOARD_URL=https://rustrak.example.com
-
-  ui:
-    image: rustrak/rustrak-ui:latest
-    ports: ["3000:3000"]
-    environment:
-      - RUSTRAK_API_URL=http://server:8080
```

Behind a reverse proxy, point the name your team opens at the server
container; the dashboard's sign-in page is `/login` on it. If you had a second
name for the dashboard, it can go, or it can proxy to the same container.

Set `DASHBOARD_URL` to the server's public address, or the issue links in
alert notifications keep pointing at the old dashboard host.

### Keep the dashboard on its own host

If the point of your setup was the machine holding the data serving no
frontend, that still works:

```yaml
services:
  server:
    image: rustrak/rustrak-server:next
    environment:
      - RUSTRAK_DASHBOARD=off
  ui:
    image: rustrak/rustrak-ui:next
    ports: ["3000:3000"]
    environment:
      - RUSTRAK_API_URL=http://server:8080
```

The browser still sees one origin, the `ui` one; nginx proxies the API
prefixes to the server.

## Go back

Change the image tag back to `latest` (or `postgres`) and restore the `ui`
service. There is no schema to undo.
