# Installation

There are several ways to run Rustrak depending on your needs. Pick the one that fits your setup.

## SQLite (default — no external database)

The default `latest` image uses SQLite. No PostgreSQL needed — data persists in a Docker volume.

```bash
docker run -d \
  --name rustrak \
  -p 8080:8080 \
  -v rustrak_data:/data \
  -e SESSION_SECRET_KEY=$(openssl rand -hex 32) \
  -e CREATE_SUPERUSER=admin@example.com:changeme123 \
  rustrak/rustrak-server:latest
```

The server starts on **http://localhost:8080**. No other services needed.

> `DATABASE_URL` defaults to `sqlite:///data/rustrak.db` — no need to set it. The Docker volume `rustrak_data` mounts at `/data` so data persists across container restarts.

### When to use SQLite

- Personal projects or solo developers
- Low to medium traffic (under ~1,000 events/hour)
- Environments where running PostgreSQL is impractical
- Trying out Rustrak quickly

## Quick install (Docker Compose — PostgreSQL)

The fastest way to get everything running locally.

### 1. Create the docker-compose.yml

Create a `docker-compose.yml` file with the following content:

```yaml
services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]
      interval: 5s
      timeout: 5s
      retries: 5
    restart: unless-stopped

  server:
    image: rustrak/rustrak-server:postgres
    ports:
      - "${SERVER_PORT:-8080}:8080"
    environment:
      - PORT=8080
      - RUST_LOG=${RUST_LOG}
      - DATABASE_URL=postgres://${POSTGRES_USER}:${POSTGRES_PASSWORD}@postgres:5432/${POSTGRES_DB}
      - SESSION_SECRET_KEY=${SESSION_SECRET_KEY}
      - CREATE_SUPERUSER=${CREATE_SUPERUSER}
      - PUBLIC_URL=${PUBLIC_URL:-}
    depends_on:
      postgres:
        condition: service_healthy
    restart: unless-stopped

volumes:
  postgres_data:
```

**What each service does:**

| Service | Description |
|---------|-------------|
| `postgres` | PostgreSQL 16 database with persistent storage. Includes a healthcheck to ensure it's ready before the server starts. |
| `server` | The Rustrak API server (Rust/Actix-web). Handles event ingestion, API requests, **and the dashboard** — the same process answers `/` and `/api`. Uses ~50MB RAM. |

### 2. Configure environment variables

Create a `.env` file with all required configuration:

```bash
# ===================
# Database (PostgreSQL)
# ===================
POSTGRES_USER=rustrak
POSTGRES_PASSWORD=rustrak
POSTGRES_DB=rustrak

# ===================
# Server
# ===================
SERVER_PORT=8080
RUST_LOG=info
# The address your SDKs will send events to. Without it the DSN carries the
# bind address, which nothing can reach. e.g. https://rustrak.example.com
PUBLIC_URL=

# Session secret (required) - replace with the output of: openssl rand -hex 32
# The server refuses to start until you do.
SESSION_SECRET_KEY=generate-your-own-with-openssl-rand-hex-32

# Admin user (required) - format: email:password
CREATE_SUPERUSER=admin@example.com:changeme123

```

> **The dashboard needs no configuration.** It is compiled into the server
> image and served from `/`, so the browser talks to the same origin the API
> answers on. There is no API address to tell it about and no second port to
> open.

> **Reverse proxy?** Behind Traefik, nginx or Caddy you can delete the `ports`
> block from `server` entirely and let the proxy reach the container on the
> Docker network. Set `PUBLIC_URL` to your public host. See
> [Reverse proxy](/configuration/production#reverse-proxy).

To generate a secure session secret:

```bash
openssl rand -hex 32
```

### 3. Start Rustrak

```bash
docker compose up -d
```

This starts:
- PostgreSQL on port 5432
- Rustrak Server on port 8080, answering both the API and the dashboard

Open [http://localhost:8080](http://localhost:8080) and log in with the credentials you set in `CREATE_SUPERUSER`.

## Server only (recommended for production)

For production, you often want minimal resource usage on your server. One
container is the whole install: it ingests events, answers the API, and hands
out the dashboard.

### On your server

**With SQLite (no external DB):**

```bash
docker run -d \
  --name rustrak \
  -p 8080:8080 \
  -v rustrak_data:/data \
  -e DATABASE_URL="sqlite:///data/rustrak.db" \
  -e SESSION_SECRET_KEY="$(openssl rand -hex 32)" \
  -e CREATE_SUPERUSER="admin@example.com:changeme123" \
  rustrak/rustrak-server:latest
```

**With PostgreSQL:**

```bash
docker run -d \
  --name rustrak \
  -p 8080:8080 \
  -e DATABASE_URL="postgres://user:pass@db-host:5432/rustrak" \
  -e SESSION_SECRET_KEY="$(openssl rand -hex 32)" \
  -e CREATE_SUPERUSER="admin@example.com:changeme123" \
  rustrak/rustrak-server:postgres
```

The server uses **~50MB RAM** and handles all error ingestion, API requests and
the dashboard.

### Access the dashboard

Open the server's own address — `http://localhost:8080`, or whatever
`PUBLIC_URL` points at. The dashboard is compiled into the image and served
from `/`, so nothing else has to run and nothing has to be configured.

**API-only deployments still work.** The dashboard is mounted only when a build
is present in the image, so a server built without one answers the API and
returns a plain JSON 404 for `/`. Point any Sentry SDK at it and never deploy a
UI — that has always been the premise, and it has not changed.

## User management

### First admin user

The admin user is created automatically on first startup using the `CREATE_SUPERUSER` environment variable:

```bash
# In your .env file
CREATE_SUPERUSER=admin@example.com:yourpassword
```

The format is `email:password`. This only creates the user if no users exist in the database yet.

## Verify the installation

1. Open the dashboard (localhost:8080, or your `PUBLIC_URL`)
2. Log in with your admin credentials
3. You should see an empty project list

You're ready to [capture your first error](/getting-started/quickstart).

## Resource comparison

| Setup | Server RAM | Server CPU | Notes |
|-------|------------|------------|-------|
| Full stack | ~200MB | Low | Easiest setup |
| Server only | ~50MB | Minimal | Dashboard runs elsewhere |
| Server only + Vercel | ~50MB | Minimal | Zero dashboard overhead |

For a 512MB VPS, the server-only option leaves plenty of room for your application and database.
