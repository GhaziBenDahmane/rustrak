## Anonymous telemetry

Rustrak runs on machines we never see, so "is this version leaking memory
for anyone?" and "does anyone still run SQLite on ARM?" were guesses. The
server now sends one `heartbeat` document, about 2 KB, every six hours. The
first one leaves ten minutes after startup, which is time to read the notice
in the log and set the switch.

- **Identity and build.** A random UUID minted on first start and stored in
  the database, never derived from the host; the version, OS, architecture,
  whether it runs in a container, the database engine and version, whether
  the dashboard is mounted, and uptime
- **Resources.** CPU count, host memory, and the process's resident memory
  over the window, sampled once a minute
- **Volume.** Projects, users, open issues, and events, transactions,
  sessions and logs in the last 24 hours, each blurred to two significant
  digits before it leaves: 4,517 events is reported as 4,500
- **Health.** Counters since the previous report: ingests accepted and
  rejected by reason, ingest latency p50 and p99, digest successes and
  failures, server errors per route *pattern* (`/api/issues/{id}`, never the
  real path), failed alert deliveries per provider kind, and panics per
  source location inside Rustrak's own code, without the message
- **Configuration.** Booleans and kinds only: whether SSL proxy, `PUBLIC_URL`,
  SMTP and a session secret are set, and which alert provider kinds exist

Never sent: IP addresses, hostnames, `PUBLIC_URL`, `DATABASE_URL`, email
addresses, project or team names, DSNs, event payloads, stack traces, error
messages, request paths, release or environment names, panic messages, log
lines. The [telemetry page](/configuration/telemetry) lists every field.

## Turning it off, and seeing what would go

```bash
RUSTRAK_TELEMETRY=off   # or DO_NOT_TRACK=1; either one is enough
```

- `RUSTRAK_TELEMETRY` accepts `on`, `off`, `true`, `false`, `1` and `0`. Any
  other value refuses to start, so a typo is never read as "on"
- The startup log says which state it is in and prints the instance id
- `GET /api/telemetry/preview`, as an admin, returns the next heartbeat
  exactly as it would leave, plus `enabled` and the reason if it is off. It
  works either way, so the decision can be made on the real document
- A binary built from source without the project's key (a fork, a local
  `cargo build`) has telemetry off and says so at startup. The published
  images receive the key as a BuildKit secret, so it never lands in the
  image metadata
- Cost on the server: one atomic increment per request, one small `/proc`
  read per minute, three count queries and one POST with a 10 second timeout
  every six hours. A failed send is a `debug` line and is not retried
